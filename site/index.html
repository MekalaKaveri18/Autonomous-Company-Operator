The loop

A plan is a living artifact, not a frozen script: any observation can revise, insert into or replace the remaining steps. And when a plan runs out, that is not the same as the work being finished — the planner is asked to carry on.

Goal→Understand→Plan→ Execute→Observe→Adapt→ Verify→Complete

Two bets

An agent's report on its own work is worthless

Agents are confidently wrong about their own success more than anything else. A form submitted into a validation error reads as a successful click. So acceptance criteria are fixed at intake, before any work exists to rationalise. Afterwards a verifier re-reads the systems of record through a registry filtered in code to read-only tools — it cannot repair what it is meant to judge — and an unmet criterion overrides the model's own completion claim.

Generalisation is architecture, not prompting

The kernel holds no domain logic and never names a tool. The proof: a second, unrelated task family was added without changing a line of the kernel, the tool base, the policy engine or the verifier. It arrived as an SOP, a YAML connector spec and one new tool surface. What this operator does lives in company/, not in its code.

Four surfaces, two task families

Finance

Accounts-payable invoice processing

Five invoices arrive as PDFs. Two are clean; one is over-billed against its purchase order; one references a PO that does not exist, from a vendor absent from the approved master; one is a duplicate. Two files are not invoices at all. An operator that approves all five is wrong — and so is one that approves two and says nothing about the rest.

IT operations

New-joiner onboarding

A prose memo, not a form. The operator derives the username from the SOP's convention, creates the account in a desktop application (writes are GUI-only — there is no API for them), issues the role's standard kit from available stock, and grants access. One requested group is restricted, so the app refuses and it must escalate.

Decisions worth arguing about

DecisionWhy
Schema-constrained JSON, never vendor tool-calling Tool-calling semantics differ enough across providers that a swap would ripple into the kernel. Changing model is now one environment variable.
Risk is computed, never self-reported The model proposes; a declarative policy engine decides. A model that could declare its own actions low-risk would eventually talk past every gate — by accident if not by injection.
Credentials never reach the model Sign-in takes an account role; the secret is resolved in the tool layer. The model can ask to act as the finance controller — and policy can refuse — but cannot read or type a password.
Refusals are not faults “This vendor is not approved” is information the SOP already covers; retrying changes nothing. A 503 should cost a retry, not a reasoning cycle. The failure taxonomy keeps the two apart.
Never blindly retry a non-idempotent action Re-firing a write risks double-executing work the first attempt may have partly completed. Found by a test: a 5xx on a form submit was being reported as success.
BM25 over company memory, not embeddings A few hundred short, jargon-dense operational documents where exact matching on PO-4471 beats semantic similarity — and it runs offline, for free.
A nine-model fallback chain The free tier meters 20 calls per day per model, so breadth multiplies capacity. A daily-quota 429 carries an eleven-hour retry delay — honouring it literally would hang a run until morning.

No agent framework. No LangChain, no vector database. The control loop, the failure taxonomy and the verification design are the substance here, and wrapping someone else's loop would have hidden exactly the parts worth evaluating.

Known limits

Stated plainly, because they are the honest edges of a prototype.

  • Verification is only as good as its criteria, and the criteria come from the model. The partial run above is a real instance: the harness behaved correctly, but the criterion the model wrote for itself was too weak. Versioned criteria libraries per task type are the fix, and the next thing to build.
  • Both computer-use surfaces are accessibility-based, not vision-based. When an accessibility tree exists this is strictly better — deterministic, no OCR, a few hundred tokens instead of pixels — but it will not drive a canvas app or a remote desktop.
  • The desktop surface is Windows-only. UI Automation is a Windows API, so on other platforms those tools are not registered at all and the operator presents only the surfaces it genuinely has.
  • Runs execute in-process. The kernel is written for a durable queue — a run is one serializable state object plus an event log — but the queue and worker recovery are not built.
  • Prompt injection is mitigated, not solved. Documents are framed as data, secrets are excluded from memory, policy is not a prompt — but a document that persuades the planner to take a permitted action in a harmful order is not caught today.
  • Free-tier models wander. The run above took 49 steps and 11 plan revisions for work a tight plan does in 23. Nothing in the architecture assumes the cheap model.

202 tests, no API key required. The full-workflow tests assert against sandbox state rather than the operator's account of it — including a run that approves an invoice but never posts it to the ledger, where the operator's own record says “completed” and verification must contradict it.
